## PART 1 — How to run it on your local device

### Prerequisites
```bash
python --version     # need 3.10+
```

### Setup (one time)
```bash
cd "F:\Full Stack\spendsmart-ml"
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

### Get a Kaggle API token (needed for real data — skip only if using --synthetic)
1. Go to kaggle.com → Settings → API → **Create New Token** → downloads `kaggle.json`
2. Place it at `C:\Users\<you>\.kaggle\kaggle.json`

### Run the full pipeline
```bash
python -m src.train                # combined real data (default): trains all 4 models
python -m src.train --synthetic    # offline demo, no credentials needed
python -m src.train --cc-only      # credit-card dataset only
```
This prints a results summary, writes `reports/metrics.json`, and saves trained models to
`artifacts/*.joblib` (categorizer, segmenter, forecaster).

### Run the smoke tests (fast, no internet needed)
```bash
python tests/test_pipeline.py
```

### Run it on your own bank/UPI statement
```bash
python -c "
import sys; sys.path.insert(0, 'src')
from data_sources import load_real_transactions   # or your own PDF-parsed transactions
# see reports/gpay_live_dashboard.html for the full worked example
"
```
(The GPay PDF → dashboard pipeline used in this project's demo is a separate script that parses
the statement with `pdfplumber`, runs it through `TransactionCategorizer.load()` +
`upi_adapter.categorize()`, then the forecaster/recommender — ask if you want that script
formalized into `src/`.)

### Run on Google Colab
Open `notebooks/SpendSmart_Recommender_Colab.ipynb` → Runtime → Run all. Add your Kaggle token in
the setup cell, or switch the training cell to `source="synthetic"` for a no-credentials run.

## PART 2 — How we measured accuracy (methodology)

Every model is evaluated two ways: **(a) a statistical held-out split** for the standard ML
metric, and **(b) a hand-labelled real-world test** for the categorizer, because a held-out split
alone can't prove the model works on data it has never structurally seen (e.g., Indian UPI text).

### (a) Categorizer — text classification
- **Split**: stratified 80/20 train/test on the labeled corpus (`train_test_split`, `stratify=category`)
- **Metric**: accuracy + macro-F1 (macro-F1 matters more — it doesn't let common categories mask poor performance on rare ones)
- **Current result**: accuracy **91.0%**, macro-F1 **90.6%** on 1,742 held-out examples
- **Corpus** (11,614 examples after augmentation, before dedup): US credit-card merchants + HuggingFace natural-language expense messages + Indian expense-tracker notes + Indian digital-wallet merchants + a generated UPI-shaped Indian brand/business-vocabulary corpus

### (b) Categorizer on REAL, never-before-seen data — the honest test
A held-out split only proves the model fits *this kind of text*. To prove it generalizes, I:
1. Hand-labelled **143 real merchants** from an actual GPay bank statement (ground truth written by reading each merchant name — not generated by any model)
2. Ran the trained model on those merchant strings it had **never seen during training**
3. Also tested **10 invented Indian merchant names** that don't exist in any dataset (e.g. `BALAJISERVICESTATION`, `ARYADENTALCLINIC`) to check it learned *vocabulary patterns*, not memorized specific names

**Results:**
| Test | Score |
|---|---|
| ML model alone, on real business merchants | **87.3%** (up from 38.0% before Indian-UPI training) |
| ML model + rule adapter, full statement (incl. P2P transfers) | **92.3%** overall |
| P2P transfers correctly identified as "no category" | **97.2%** |
| Unseen invented Indian merchants | **10/10** |

### (c) Forecaster — regression (next-month spend prediction)
- **Split**: per-user temporal split — each user's **last observed month is held out**, trained only on their earlier months (not a random split — random splits would leak future data backward for the same user, which is unrealistic and inflates scores)
- **Metrics**:
  - **MAE** (Mean Absolute Error) — average ₹ error
  - **WAPE** (Weighted Absolute Percentage Error = Σ|error| / Σ|actual|) — used instead of MAPE because MAPE explodes to meaningless numbers when many actual values are ₹0 (a common case — not everyone spends in every category every month)
  - **Skill vs. naive baseline** — how much better than simply predicting "same as last month"
- **Current result**: MAE ₹271 vs naive ₹291, WAPE 0.774, **skill +6.9%** (beats the naive baseline)
- **Model**: one HistGradientBoostingRegressor **per category** (11 separate models), trained on lag features (previous 1-3 months), rolling mean/std, income, month-of-year

### (d) Segmentation — unsupervised clustering
- **Metric**: silhouette score (measures how well-separated the clusters are; range −1 to 1, 0 = overlapping)
- **Current result**: 0.230 (6 KMeans cohorts over 1,927 users)
- Note: silhouette is inherently lower for real, messy human behavioral data than for synthetic data — a "good" score here is anything meaningfully above 0

### (e) Overspend detector — binary classification (recommendation quality)
- **Ground truth definition**: a (user, category, month) is a true overspend if actual spend exceeds that user's own trailing mean + 1.5σ
- **Metrics**: precision, recall, F1 — compared against the same rule driven by the naive baseline instead of the trained forecaster
- **Current result**: model F1 **0.433** (precision 0.326, recall 0.642) vs. naive F1 **0.237** — nearly **2× better** than naive

### Why this methodology is defensible
- No metric is self-reported without a baseline comparison (naive last-month, or naive threshold)
- The forecaster split respects time order per-user — no data leakage
- The categorizer's headline number is the **real-statement test**, not the held-out split, because that's the number that matters for "does it actually work"
- WAPE was deliberately chosen over MAPE after finding MAPE gave a misleading 469% error on sparse categories

## PART 3 — Anticipated jury questions and answers

### Project scope & motivation

**Q: What problem does this solve, and how is it different from apps like Walnut/Money View/ET Money?**
A: Those apps mostly categorize transactions and show pie charts. This project adds three layers
those don't: (1) a **personalized forecaster** that predicts *your* next month's spend per category
using gradient boosting on *your* lag history — not a global average; (2) **cohort-based peer
comparison** via unsupervised clustering, so "you spend more than average" is judged against
financially similar users, not everyone; (3) a **budget-reallocation optimizer** that suggests
concrete category cuts to hit a savings goal, with a real-time O(categories) update path for
streaming transactions — no retraining needed as new transactions arrive.

**Q: Why is this "personalized" and not just another categorizer?**
A: Three layers of personalization: (1) self-baseline — every anomaly is judged against *that
user's own* mean/std, not a population norm; (2) personalized forecast — the regressor is fit
per-category on lag features, so the prediction is conditioned on the individual's history; (3)
cohort context — peer comparisons use K-means-assigned cohorts of similar users, not a global
average, so a student isn't compared to a homeowner.

### ML / algorithms

**Q: What ML algorithms did you use, and why these specifically?**
A: Four models: (1) **TF-IDF (word + char n-grams) → Logistic Regression** for transaction
categorization — char n-grams make it robust to spelling/spacing noise in real merchant strings,
and logistic regression is fast, interpretable, and doesn't need GPU; (2) **KMeans** for user
segmentation — standard, interpretable, and the silhouette score gives a built-in quality check;
(3) **HistGradientBoostingRegressor** (one per expense category) for forecasting — handles
non-linear relationships and mixed-scale features (lags, rolling stats, income) without heavy
tuning, and is CPU-fast enough for the notebook demo; (4) the recommender/overspend detector is
**not learned** — it's a deterministic z-score threshold + greedy budget-reallocation optimizer,
which keeps it fast enough for the real-time update path.

**Q: Why not deep learning / transformers / an LLM?**
A: The data volumes per user are small (months of data, not millions of rows), and the categories
are a fixed, closed taxonomy — a use case where classical ML (TF-IDF+LR, gradient boosting)
matches or beats deep learning while running instantly on CPU with no GPU cost, which matters for
a real-time, cheaply-deployable personal finance tool. A transformer would add latency and cost
without a clear accuracy win at this data scale.

**Q: How did you prevent overfitting?**
A: (1) All evaluation uses held-out data the model never trained on — stratified splits for the
categorizer, per-user temporal holdout for the forecaster; (2) logistic regression uses
`class_weight="balanced"` and L2 regularization (`C=4.0`); (3) gradient boosting models are
shallow, fast-fitting models rather than deep ensembles; (4) the *decisive* proof against
overfitting is the 10/10 score on **invented merchant names that exist nowhere in training data**
— if the model had memorized rather than generalized, that test would fail.

**Q: What is macro-F1 and why report it alongside accuracy?**
A: Accuracy can look good even if the model is only good at the majority classes. Macro-F1
averages the F1 score *per class* equally, so it penalizes poor performance on rare categories
(e.g. "financial", "subscriptions") that accuracy alone would hide.

**Q: What is WAPE and why not just use MAPE or RMSE?**
A: WAPE = Σ|error| / Σ|actual| (weighted by total spend, not per-row). MAPE (Mean Absolute
Percentage Error) divides by each individual actual value — when a user spends ₹0 in a category
that month, the percentage error explodes toward infinity, giving a meaningless headline number
(we measured this directly: MAPE reported 469% on our data). WAPE avoids that by dividing the
*sums*, giving a stable, interpretable single number.

**Q: How does the recommender/optimizer actually work?**
A: For a savings goal, it ranks categories by "flexibility" (how compressible that spend has
historically been for that user) and greedily proposes cuts starting from the most flexible
category until the target is reached or categories run out — a simple, fast, explainable
heuristic rather than a black-box optimizer, which matters because financial advice needs to be
justifiable to the user.

### Data

**Q: What data did you train on — is it real or synthetic?**
A: Real, by default. The pipeline combines: 1.3M real Kaggle credit-card transactions (983 users,
18 months), a Kaggle personal-finance-tracker dataset (944 users with real income/rent/loan data),
plus Indian-specific data for UPI support — real Indian expense-tracker notes, digital-wallet
merchant names, and 20,000 real Indian users' income/spending profiles for cohort norms. A
synthetic generator (`src/synth.py`) exists only as an offline, zero-credential fallback.

**Q: How much data, exactly?**
A: ~1.3M transactions, ~1,900 unique users for the core pipeline; the categorizer's labeled corpus
is ~11,600 (description, category) pairs after combining and augmenting all sources; the Indian
cohort model is fit on 20,000 real Indian users.

**Q: How did you validate the model actually works on Indian/UPI data specifically, not just US card data?**
A: I didn't rely on the training-split number for this claim. I hand-labelled 143 real merchants
from an actual GPay statement as an independent, real-world test set the model never trained on,
and separately tested 10 invented Indian merchant names not present in any dataset. That's the
92.3% / 87.3% / 10-of-10 numbers above.

**Q: What happens to person-to-person transfers (like paying a friend)?**
A: They're deliberately labeled `transfer`, not forced into a spending category — a payment to
"Rohit" carries no inherent category, and guessing one would be a worse answer than admitting
it's unclassifiable. A person-name heuristic (business-keyword absence + all-alphabetic pattern)
plus low model confidence routes these correctly, measured at 97.2% correct identification.

**Q: Is there a cold-start problem — what about a brand-new user with no history?**
A: The categorizer and segmenter work immediately (they're pre-trained, not per-user). The
forecaster needs at least a few months of that user's lag history before it can predict — for a
brand-new user, the system would fall back to cohort/population averages until enough personal
history accumulates. This is a known, stated limitation, not hidden.

### Evaluation & metrics

**Q: What's your current accuracy?**
A: Depends on which model: categorizer 91.0% accuracy / 90.6% macro-F1 (held-out split), 92.3% on
the real hand-labelled GPay test; forecaster MAE ₹271 (beats naive by 6.9%); segmentation
silhouette 0.230; overspend detector F1 0.433 (nearly double the naive baseline's 0.237).

**Q: Why is the overspend detector's F1 only 0.43 — isn't that low?**
A: In isolation it looks modest, but the comparison that matters is against the naive baseline
(F1 0.237) on the *same* task — the model is achieving 82% relative improvement over the naive
approach. Overspend detection from limited history is a genuinely hard, noisy problem; reporting
it against a fair baseline rather than an arbitrary "0.9 is good" bar is the honest framing.

**Q: Why is the segmentation silhouette score only 0.23 — is that bad?**
A: Silhouette near 0.2-0.3 is typical and expected for real human behavioral data with overlapping
spending patterns — a "perfect" score near 1.0 would actually be suspicious, implying artificially
separable (likely synthetic-looking) clusters. Six cohorts remain meaningfully separated, which is
what the downstream peer-comparison feature needs.

**Q: Did you compare against any other algorithms before choosing these?**
A: For the categorizer, TF-IDF+LR was chosen over pure word-level TF-IDF because char n-grams
measurably improved robustness to real-world merchant string noise (tested directly on the GPay
statement). For the forecaster, gradient boosting was chosen over a plain linear/naive model
specifically because the evaluation harness (`evaluate.py`) always benchmarks against a naive
"last month" baseline — the whole design forces every model to prove it beats the simple
alternative, not just report a number in isolation.

### Limitations (be ready to state these proactively — it reads as rigor, not weakness)

**Q: What are the current limitations of this project?**
A: (1) The forecaster's Indian-specific validation is limited — a dataset with genuinely dense
per-user Indian transaction history (needed for reliable per-user forecasting) wasn't available
publicly, so that model still trains primarily on the global (mostly US) panel; I explicitly
tested and *rejected* one Indian dataset for this because it only had ~5 transactions per user,
too sparse to trust. (2) Recommendations on very short histories (e.g. 3 months of a real
statement) produce statistically thin "N-sigma above usual" claims — more history is needed for
those to be reliable. (3) ~46% of real UPI statement value is person-to-person transfers with no
inherent category — a structural ceiling, not a model gap. (4) No deep personalization for
irregular/gig income patterns yet.

**Q: What would you do with more time / as future work?**
A: Collect or license a dataset with dense per-user Indian transaction history to properly
validate/retrain the forecaster for the Indian market; extend the real-time layer to actually
retrain incrementally rather than only reweight; add multi-currency support; build a proper
UPI-handle (`@paytm`, `@oksbi`) parser to recover a few more percent of categorizable spend.

### Engineering / deployment

**Q: Is this production-ready? How would you deploy it?**
A: It's a training/evaluation pipeline plus saved `.joblib` artifacts today, not a deployed
service. Deployment would wrap the loaded artifacts (`categorizer.joblib`, `segmenter.joblib`,
`forecaster.joblib`) behind an API — since everything is scikit-learn, inference is CPU-only and
fast (no GPU serving needed), which keeps hosting cheap.

**Q: How does the real-time update work without retraining?**
A: `recommender.RealTimeState` keeps rolling per-category mean/std for a user. When a new
transaction arrives, it updates those aggregates in O(number of categories) and recomputes
projected month-end totals and alerts instantly — the *trained* forecaster/segmenter parameters
don't change, only the lightweight per-user state does, so no retrain is needed for live alerts.

**Q: What about data privacy — this is sensitive financial data?**
A: All processing in this project runs locally / offline; the GPay statement demo parsed a local
PDF into transactions in-process and was never uploaded anywhere. Any real deployment would need
standard safeguards (encryption at rest, no third-party data sharing) that weren't the focus of
this ML-pipeline project but are a stated next step.

**Q: How do you handle multiple currencies / non-INR income?**
A: Not currently — the pipeline assumes a single currency per user (₹ in the demo). Documented as
a future-work item, not silently ignored.
